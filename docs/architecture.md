# 架构说明

这里只写已经定下的设计。还没定的标"待确认"，数值按假设先实现的标"v0 假设"。每个阶段完成时同步更新本文。

## 范围

| 归平台服管 | 不归平台服管 |
|---|---|
| 账号、会话、鉴权 | 对局里的判定（由战斗服负责，见 [ADR 0002](adr/0002-battle-server-as-unity-dedicated-server.md)） |
| 开局：房间码、匹配 | 游戏内的命令和快照同步 |
| 拉起、监控、回收战斗服进程 | 客户端热更新资源的分发（另走文件服务器） |
| 结算、rating、战绩、排行榜 | |
| 监控指标 | |

## 组件

```
                    ┌──────────────────────── echo-platform ────────────────────────┐
Unity 客户端 ──HTTP──► controllers ──► services ──► repositories ──► MySQL / Redis │
            ──WS────►  （解析、校验）    （业务）       （存储）                      │
                    │                     │                                         │
                    │                     └──► IAllocator ──posix_spawn──► 战斗服进程 │
                    │  内部监听 ◄──────── 就绪 / 心跳 / 结果 ─────────────────────┘   │
                    └────────────────────────────────────────────────────────────────┘
```

- **分层**：controllers → services → repositories，只能单向依赖。
  - Controller 只做请求解析、参数校验和错误格式转换。
  - 各服务在 `main` 里构造好再注入，不用单例。
- **对外和对内分开监听**：
  - 对外端口给客户端用：HTTP 和 WebSocket。
  - 内部端口只给战斗服用，绑定在内网地址上，每个战斗服带自己的令牌。
- **匹配核心**（`libs/matchmaking`）：纯 C++ 库，不做 IO，输入是队列和当前时间，输出是配好的对。可以单独测试和压测。

## 开局流程

```
客户端A/B ──登录──► 平台服 ──会话 token──► 客户端
客户端A/B ──WS 入队或输房间码──► 平台服：配成一对
平台服 ──拉起战斗服（端口、对局 id、对局密钥）──► 战斗服 ──就绪──► 平台服
平台服 ──match_found（地址、端口、加入票据）──► 客户端A/B ──连接（带票据）──► 战斗服
战斗服 ──每隔几秒发心跳──► 平台服
战斗服 ──结果──► 平台服：一个事务写入战绩和 rating ──► 更新排行榜
```

- **两种开局方式**：
  - **房间码**：一方创建房间拿到短码，另一方输码加入。这是实际对战时主要的用法。
  - **匹配**：按 rating 配对，窗口随等待时间扩大，主要用来展示后端能力和压测。
  - 两者配好对以后，后面走同一条流程。
- **超时（v0 假设）**：
  - 战斗服 20 s 内没有就绪，就回收进程，玩家回到队列；
  - 心跳断了 15 s，就判这局中止。
- **断线重连**：玩家断线后，凭会话 token 向平台服要一张新的加入票据，再连回同一个战斗服。战斗服给每个玩家留的重连时间，按游戏规则是 30 s。

## 数据

**MySQL（以它为准）**：

| 表 | 主要字段 | 说明 |
|---|---|---|
| `users` | id、用户名、密码哈希（Argon2id）、rating、创建时间 | 游客账号没有用户名和密码 |
| `matches` | match_id（唯一）、状态、比分、时长、状态哈希、结束时间 | 结果按 match_id 去重，重复上报只记一次 |
| `match_players` | 主键 (match_id, user_id)、席位、rating 变化 | |

- 迁移脚本放在 `db/migrations/`，按 Flyway 命名（`V0001__init.sql`）。启动时对照 `schema_migrations` 表执行还没跑过的脚本。
- 对局历史用游标分页（按 `(ended_at, match_id)`），不用 OFFSET。

**Redis（缓存和临时数据，丢了能恢复）**：

| 键 | 内容 | 丢失后 |
|---|---|---|
| `session:{token 哈希}` | 用户 id，TTL 7 天（v0 假设） | 用户重新登录 |
| `room:{房间码}` | 房主和状态，TTL 10 分钟（v0 假设） | 重新建房 |
| `lb:rating`（ZSET） | 排行榜 | 发现为空时从 MySQL 重建 |

## 并发

- drogon 跑多个 IO 线程处理请求。
- 匹配队列只归一条事件循环所有，其他线程要改队列都把操作投递到这条循环上执行，所以不加锁。匹配器在这条循环上每 200 ms 跑一轮（v0 假设）。
- 数据库和 Redis 都用异步客户端，用协程写，不阻塞 IO 线程。

## 错误处理

- HTTP 错误统一用 RFC 9457 Problem Details 格式（`application/problem+json`），带 `type`、`title`、`status`、`detail`。
- 业务错误用返回值表达，异常只在 IO 边界捕获，转成对应的 HTTP 状态码。
- 日志里不打印密码、token 和票据。

## 配置

- 按 12-factor 管理：配置文件放非敏感的设置，密钥只从环境变量读。仓库里只提交 `.env.example` 和 `config/platform.example.json`。

## 可观测性（S4）

- 用 Prometheus 指标监控：队列长度、匹配等待时间的直方图、活跃战斗服数、HTTP 延迟、战斗服上报的 tick 耗时。
- 用 Grafana 看板展示。

## 测试

| 类型 | 范围 | 运行方式 |
|---|---|---|
| 单元测试 | 匹配库、Elo、票据、输入校验 | `ctest -L unit` |
| 集成测试 | 迁移、存储层、结算去重、并发结算 | 先 `docker compose up -d`，再 `ctest -L integration` |
| 端到端 | 两个机器人分别走房间码和匹配，假战斗服上报就绪和结果 | `apps/loadtest` 的场景模式 |
| 压测 | 1000 和 5000 并发排队，记录 p50、p99 和 CPU | `apps/loadtest`，结果只写实测值 |
