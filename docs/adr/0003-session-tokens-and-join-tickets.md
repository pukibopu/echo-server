# ADR 0003：会话 token 和加入票据分开

- **状态**：已采纳
- **日期**：2026-10-30

## 背景

客户端要在两个地方证明身份，两处的需求不一样：

| 场景 | 频率 | 需求 |
|---|---|---|
| 访问平台服 | 每个 HTTP 请求和 WebSocket 连接 | 登出或封禁时要立刻失效；能查到当前用户 |
| 进入战斗服 | 每局开始时一次，断线重连时再来一次 | 战斗服生命期短，可能跑在别的机器上，最好不依赖 Redis 或 MySQL |

考虑过的方案：

- **全部用 JWT**：战斗服能直接验证，但登出和封禁没法立刻生效，要另做黑名单。
- **全部用不透明 token**：战斗服每次都得回调平台服或查 Redis 才能验证，多一个依赖和一次往返。
- **分开处理**：两处各用合适的机制。

## 决定

**会话 token**（访问平台服）：

- 登录时生成 256 位随机数，编码后发给客户端。
- Redis 里存 `session:{SHA-256(token)}` 到用户 id 的映射，TTL 7 天（v0 假设）。存哈希而不存原文，Redis 数据泄露时拿到的值也不能直接冒用。
- 登出时删掉这个键，立刻失效。

**加入票据**（进战斗服）：

- 平台服每分配一局，就生成一个随机的对局密钥，拉起战斗服时通过环境变量传给它。
- 匹配成功后，平台服用这个密钥对票据做 HMAC-SHA256 签名，票据内容是对局 id、用户 id、席位和过期时间，有效期 60 s（v0 假设）。
- 战斗服在 NGO 的连接审批（ConnectionApproval）里校验签名和过期时间，并核对这个席位是不是这名用户。
- 具体格式在 S3 写进 `docs/ticket.md`。

## 后果

- **好处**：
  - 会话可以随时吊销；
  - 战斗服验证票据不需要访问任何存储；
  - 一局的密钥泄露，只影响这一局。
- **代价**：要维护两套机制。
- **风险**：票据签发后不能提前作废，靠很短的有效期来限制风险。断线重连要再向平台服要一张新票据。
