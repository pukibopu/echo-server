# ADR 0002：战斗服用 Unity 专用服构建

- **状态**：已采纳
- **日期**：2026-10-30

## 背景

《回波》的规则层是 C# 写的，不引用任何 Unity 组件，只用到 Unity 的数学类型（`Vector3`、`Mathf`）。碰撞查询都经过一个接口（`IPhysicsQuery`）：

- 视线判定运行时用 `Physics.Linecast`；
- 角色移动用隐藏的 `CharacterController` 处理贴墙滑动、坡道和台阶。

规则层按 30 Hz 固定 tick 运行，客户端只发命令、只收按感知过滤后的快照，这样从源头上防止透视。

原来的联机设计是 Netcode for GameObjects（NGO）的主机模式，由一名玩家当主机。这种做法有两个问题：

- 主机方没有网络延迟，对局不公平；
- 跨公网联机要做 NAT 穿透或中继。

考虑过的方案：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 保留主机模式，加中继 | 改动最小 | 主机方零延迟不公平；中继还是得有服务端 |
| **Unity 专用服构建** | 规则层和物理跟客户端是同一份代码，判定天然一致；从 NGO 主机模式改成服务器模式改动小 | 每局一个进程，占用的内存比纯 .NET 大（未测量） |
| 规则层移植到纯 .NET 服务器 | 进程轻，一个进程能跑多局 | 要自己写地图碰撞导出、射线和胶囊移动，还要和 `CharacterController` 的行为一致，否则客户端预测会频繁被拉回；工作量多 2–3 周（估计） |

## 决定

- 战斗服用 Unity 的 Dedicated Server 构建（Linux），NGO 跑服务器模式，两名玩家都作为客户端连进来。
- 每局一个进程，由平台服的分配器拉起、监控和回收。
- 移植到纯 .NET 放到以后再考虑。

## 后果

- **好处**：
  - 判定和客户端预测用同一份规则和物理；
  - 双方都有网络延迟，对局对称；
  - 战斗服里不用重新实现游戏逻辑。
- **代价**：
  - 平台服要管理进程，包括端口池、就绪超时、心跳和回收（见 S3）；
  - 单机能同时开的对局数受进程内存限制，要实测。
- **对平台服的要求**：
  - 战斗服启动后通过内部接口上报就绪，运行期间定时发心跳，结束时上报结果；
  - 玩家进战斗服时凭平台服签发的加入票据（见 [ADR 0003](0003-session-tokens-and-join-tickets.md)）。
