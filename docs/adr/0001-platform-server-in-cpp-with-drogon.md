# ADR 0001：平台服用 C++20 和 drogon

- **状态**：已采纳
- **日期**：2026-10-30

## 背景

平台服要提供这些能力：

- HTTP 接口：登录、战绩、排行榜；
- WebSocket 长连接：推送匹配状态；
- 读写 MySQL 和 Redis；
- 拉起和管理战斗服进程。

项目由一个人开发。它既是游戏的一部分，也是求职作品，要同时给游戏客户端和后端两类岗位看。作者最熟悉的语言是 C++。

考虑过的方案：

| 方案 | 优点 | 缺点 |
|---|---|---|
| Go | 开发快；国内互联网后端常用 | 作者要从头学，三个月内很难学到经得起面试深挖的程度 |
| Java（Spring Boot） | 国内后端岗位最多 | 框架重，一个人写配置和样板代码的量大；同样要从头学 |
| C#（ASP.NET Core） | 和 Unity 客户端同一种语言 | 国内后端岗对它认可度低 |
| C++ + 自己写网络层（Asio） | 能讲 Reactor、epoll、定时器 | 多 1.5–2 周（估计）；容易做成又一个 TinyWebServer，精力被底层占掉 |
| **C++ + drogon** | 发挥作者的长处；框架自带 HTTP、WebSocket，以及 MySQL 和 Redis 客户端，支持 `co_await` | 开发速度比 Go 慢；生态比 Java 小 |

## 决定

- 用 C++ 开发，编译标准设为 C++20。代码主体按 C++17 的习惯写，只在异步 IO 处（数据库、Redis、HTTP 客户端）用 C++20 协程。国内的存量代码多停在 C++11/14，新项目大多用 C++17；这样写，读者看着熟悉，异步代码也不用层层嵌套回调。
- Web 框架用 drogon。网络层直接用框架的，精力放在业务设计上：匹配算法、拉起战斗服、防止重复结算、排行榜。
- 匹配和 Elo 写成不做 IO 的纯 C++ 库（`libs/matchmaking`），可以单独测试和压测。

## 后果

- **好处**：
  - 发挥作者的 C++ 长处；
  - 异步代码用协程写，顺序清晰；
  - 依赖少，HTTP、WebSocket、MySQL、Redis 都由同一个框架提供。
- **代价**：
  - 开发速度比 Go 慢；
  - 投 Java 或 Go 为主的后端岗时，语言不对口。只能靠和语言无关的设计（存储、并发、幂等、可观测性）来弥补。
- **风险**：
  - drogon 用 MariaDB Connector/C 连 MySQL，和 MySQL 8 默认的 `caching_sha2_password` 认证可能不兼容，S0 先验证；
  - 退路是让 MySQL 用户改用 `mysql_native_password`，或者换 PostgreSQL。
